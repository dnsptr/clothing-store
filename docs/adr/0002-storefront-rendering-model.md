# ADR-002: Модель рендеринга витрины

- **Статус:** принят
- **Дата:** 2026-07-26
- **Контекст roadmap:** задача 1.1 (этап P1); разблокирует 4.1 (медиа), 4.5 (SEO)
- **Связан с:** ADR-001 §6 (режимы данных витрины)

## Контекст

Витрина собиралась в единственном режиме `output: "export"`. Следствия:

1. Страницы товаров существовали только для id, перечисленных в
   `generateStaticParams()`, а тот возвращал id демо-каталога. Товар, заведённый
   менеджером в Medusa Admin, **не получал страницы вообще** — не медленную, не
   пустую, а 404 по прямой ссылке. Это делало админку непригодной для основной
   операции: завести товар.
2. `next/image` работал только с `unoptimized: true`.
3. `NEXT_PUBLIC_*` вшивались в бандл на сборке, поэтому смена ключа или адреса
   бэкенда требовала пересборки. Именно этот механизм привёл к деградации
   каталога на проде (roadmap 0.1).
4. PDP держала костыль: серверный компонент отдавал мок-«оболочку», а клиент
   заново дорезолвливал товар по handle.

Демо на GitHub Pages при этом остаётся нужным: у него нет сервера.

## Решение

### 1. Две цели сборки вместо одной

- `npm run build` — сервер + ISR. Артефакт Vercel. Значение по умолчанию.
- `npm run build:pages` (`BUILD_TARGET=pages`) — статический экспорт. Артефакт
  GitHub Pages. Включает `output: "export"`, `images.unoptimized`,
  `basePath`/`assetPrefix`.

CI собирает **обе** цели. Регрессия в экспортной цели иначе обнаруживается
только падением деплоя Pages.

### 2. Страницы товаров генерируются по требованию

На серверной цели `generateStaticParams()` возвращает пустой массив. По
документации Next 16 это и есть условие ISR-генерации путей в рантайме: любой
id, включая созданный после деплоя, рендерится при первом обращении и дальше
отдаётся из кеша. `revalidate = 300`.

Next 16 **не** кеширует `fetch` по умолчанию (в 14 кешировал), поэтому серверные
чтения каталога явно передают `next.revalidate`; одного сегментного
`export const revalidate` недостаточно.

### 3. Разграничение 404 и недоступности бэкенда

- Товар отсутствует в Medusa → `notFound()`.
- Medusa недоступна → контролируемое состояние ошибки, **не** 404 и **не** 500.

404 в этом случае сообщил бы покупателю, что товара не существует, и отравил бы
ISR-кеш отрицательным ответом для живого товара. Фолбэк на демо-каталог
запрещён (ADR-001 §6).

### 4. Серверные переменные окружения имеют приоритет

На сервере `MEDUSA_BACKEND_URL` / `MEDUSA_PUBLISHABLE_KEY` / `DATA_MODE`
перекрывают `NEXT_PUBLIC_*` и читаются при старте процесса. Рендеринг каталога и
карточек перестаёт зависеть от того, что вшито в бандл.

Ограничение: корзина ходит в Store API из браузера и по-прежнему требует
публичного ключа в бандле. Перенос этих вызовов за route handler — отдельная
задача, в этом ADR не решается.

### 5. `images.remotePatterns` остаётся сборочной настройкой

Next не перечитывает её в рантайме. Список выводится из адреса бэкенда плюс
`MEDIA_ALLOWED_ORIGINS`, чтобы миграция медиа в S3 (4.1) была сменой переменной,
а не правкой кода. Это единственная оставшаяся сборочная привязка к адресам.

## Последствия

- 4.5 (SEO-пакет) становится осмысленным: появились per-product `metadata`,
  канонические ссылки и OG. `sitemap`/`robots` — в рамках 4.5.
- 4.1 (медиа в S3) больше не блокируется отсутствием оптимизации изображений.
- Демо на Pages сохраняется без изменений в поведении, но собирается другой
  командой; workflow обновлён.
- Отказ от `output: "export"` на серверной цели означает, что Vercel-деплой
  теперь имеет серверную часть: это влияет на биллинг и на требования к
  мониторингу (4.2).
