## 2. Архитектурное решение по интеграции с Т-Банком

### Чек № 1 (Предоплата 100% при оформлении заказа)
1. **Кто фискализирует:** Т-Банк через облачный шлюз АТОЛ Онлайн.
2. **Как настраивается:**
   - Клиент самостоятельно заходит в ЛК Т-Бизнес (*Интернет-эквайринг → Магазины → Онлайн-касса → АТОЛ Онлайн*).
   - Вводит API-данные из файла «Настройки интегратора» (online.atol.ru): login, password, group_code и выбирает **ФФД 1.2**.
   - **Важно:** Разработчикам не требуется доступ к банку-клиенту и не требуется хранить API-пароли АТОЛа на сервере магазина для пробития чека предоплаты.
3. **Что делает бэкенд магазина (Medusa v2):**
   - В запросе `Init` в Т-Банк передается объект `Receipt`:
     - Email / Phone покупателя
     - `Taxation: usn_income`
     - Массив `Items`: наименование, сумма, количество, `Tax: vat105`, `PaymentMethod: full_prepayment`, `PaymentObject: commodity`.
   - При успешной оплате Т-Банк сам отправляет чек в АТОЛ Онлайн.

### Чек № 2 (Закрывающий чек и выбытие маркировки «Честный ЗНАК»)

Поскольку обувь и одежда подлежат обязательной маркировке, в момент сборки/отгрузки заказа:
1. Сотрудник склада сканирует код DataMatrix с упаковки.
2. Система отправляет закрывающий чек «Полный расчет» с `Tax: vat5`, `PaymentMethod: full_payment` и кодом маркировки (тег 1163 / объект `MarkCode` типа GS1M).
3. **Канал отправки:** Через API Т-Банка `/cashbox/SendClosingReceipt` (используя имеющиеся TerminalKey и Password) либо через прямой REST API АТОЛ Онлайн.
4. ОФД «Такском» автоматически передает код выбытия в систему «Честный ЗНАК».

## 4. Offline-аудит уведомлений о фискализации

Бэкенд принимает на существующем `POST /hooks/payment/tbank` подписанные уведомления о фискализации и **сохраняет их до ответа `OK`** в отдельный журнал `tbank_fiscal_notification`. Неверная подпись получает 401 без записи; сбой записи — 500, чтобы банк мог повторить доставку. Повтор идентичного подписанного тела не создаёт вторую запись, но разные ошибки/статусы для одного платежа сохраняются отдельно. Платёжный журнал, захват платежа и состояние заказа такие уведомления **не изменяют**.

В журнале только ограниченные скалярные поля: идентификаторы платежа/заказа и фискального документа, код и очищенное/усечённое сообщение об ошибке, результат корреляции. `Receipt`, контакты покупателя, пароль и токен не сохраняются. Неизвестные платёжному обработчику статусы, явные ошибки фискализации, неверные связи с оплаченной сессией и недостаточные данные попадают в `manual_review`. Даже состояние `observed` означает **только получение и сверку сигнала**, не подтверждение регистрации чека в ОФД. Администратор просматривает ограниченный список ошибок через `GET /admin/tbank/fiscal-notifications` (`offset`, `limit`); решать проблему и сверять чек с АТОЛ/ОФД нужно вручную. Автоматического повторного пробития, закрывающего чека или возврата по этому сигналу нет.

Классификация опирается на подписанные верхнеуровневые скалярные признаки и неизвестный статус; вложенный `Receipt` не входит в подпись и не должен перенаправлять платёжное уведомление. Формат реального `NotificationFiscalization` в нашем терминале пока не проверен подписанным образцом: [документация уведомлений Т-Банка](https://developer.tbank.ru/eacq/intro/developer/notification/), [сгенерированная схема API (сторонний источник)](https://jsr.io/@kravets/t-kassa-api/doc/openapi). При совпадении всех признаков с платёжным уведомлением его нельзя достоверно отличить без реального образца — не считать этот журнал доказательством выдачи чека.
В частности, один только `ErrorMessage` или `Url` при известном платёжном статусе оставляем платёжному обработчику: эти поля не доказывают тип уведомления. Если банк отправит фискальную ошибку именно в таком неотличимом формате, отдельный фискальный журнал её не увидит; прежде чем включать этот маршрут в production, нужен подписанный реальный образец и подтверждённое правило разграничения.

**Выпуск в production заблокирован:** сначала независимая внешняя проверенная резервная копия PostgreSQL и загруженных медиа с проверкой восстановления; затем отдельно согласованный контролируемый платёж с проверкой статуса фискализации в банке, АТОЛ и ОФД. Текущие миграция и offline-тесты не заменяют этих проверок. Чек № 2 из раздела 2 — проектное описание, его отправка из Medusa ещё не реализована.
