## 1. Цель первого запуска

Запустить интернет-магазин одежды Mario Mikke для России: актуальный каталог,
оформление и оплата заказа, доставка, корректные чеки, работа с маркировкой,
реальные остатки по магазинам и обработка заказов сотрудниками.

Вне первого запуска: СНГ, мультивалютность, промокоды, расширенная программа
лояльности и подключение дополнительных служб доставки, кроме утверждённых для
первого релиза.

## 2. Что уже есть

- Next.js-витрина: главная, каталог, карточка товара, избранное, корзина и

- Medusa backend с PostgreSQL, Redis и русифицированной админкой.
- Контент главной и каталог управляются через админку.
- Медиа загружаются через backend; production-развёртывание настроено на
  сервере Timeweb Cloud, API доступен через `api.mariomikke.shop`.
- Информационные страницы и чекбокс согласия в checkout существуют, но их
  юридический текст пока содержит черновые данные и должен быть заменён
  утверждённой редакцией.
  Локальные HTML и скачиваемая оферта приведены к предпусковой редакции
  19.10.2026: хранение самовывоза 7 календарных дней, выдача 10:00–22:00,
  фиксированная платная доставка перевозчиков и один онлайн-платёж.
  Сохранены предпусковые пометки; утверждение продавцом/юристом ещё требуется.
  См. [перечень юридических правок](LEGAL_PAGES_REVIEW.md).
  Эти изменения не опубликованы на Vercel.

### Checkout и безопасность — локально, не развернуто

- Воспроизведено: одного publishable key и чужого ID было достаточно для
  чтения корзины/заказа с персональными данными. Теперь гостевые корзины,
  платежи и заказы защищены отдельным случайным `x-cart-access-token`;
  в БД хранится SHA-256 токена. Авторизованный покупатель читает свои заказы.
  Чужие/отсутствующие токены дают `404`, ответы не кешируются.
- Повторное использование адреса чужой корзины по строковому ID запрещено;
  checkout передаёт адрес объектом. Старые гостевые корзины без токена не
  переиспользуются: cutover требует обновления backend и витрины вместе.
- Перед банковским переходом сверяются сумма, валюта и HTTPS-хост сессии.
  URL возврата не подтверждает оплату. В реальном браузере на изолированной
  PostgreSQL поддельный `Status=CONFIRMED` не показал успешную оплату и
  сохранил товары; после подписанного webhook появился оформленный заказ
  и корзина очистилась. Банковский `Init` был офлайн, реального списания нет.
- Загрузки ограничены пассивными медиа, сигнатурами и размером; Caddy
  добавляет sandbox CSP, лимит тела и проверку источника HTTPS-прокси.
  Проверены отказ неавторизованному покупателю в Admin API, `400` для SVG
  и поддельного PNG, HTTPS-редирект до Basic auth, `401` для панели без
  Basic auth и `413` для слишком большой загрузки.
- Next.js обновлён до `16.4.0`, Playwright до `1.64.0`; обновлены уязвимые
  backend-зависимости. 19 октября полный Docker image собран и запущен:
  Node `22.23.2`, Admin с `NODE_ENV=production`, runtime-зависимости через

  Проверены PostgreSQL 15, Redis 7, checkout, Caddy и сохранность заказа/медиа
  после пересоздания контейнера. Подробности —
  [в Docker-отчёте](DEPLOYMENT_2026-09-05.md#полный-docker-image--19-октября-2026).
- Аудит зависимостей **не нулевой**: остаются advisory в транзитивных
  инструментах и админке Medusa. Перечень и границы проверки —
  [в deployment guide](../medusa-prototype/DEPLOYMENT.md).
  Миграция checkout-доступа и защиты на рабочем сервере не применялись.
- 12–13 октября повторно проверены опубликованная витрина и рабочий сервер:
  checkout закрыт, банковский контур DEMO, новые checkout/polling-миграции

### Интеграции

- Т-Банк: написан платёжный провайдер, webhook и тесты. Тестовый DEMO-терминал
  проверен с IP production-сервера: ключ и подпись принимаются банком.
  26 сентября локально проверен checkout через реальный Store API Medusa и
  изолированную PostgreSQL: RUB-корзина с тестовым товаром и доставкой,
  фискальный чек, одна запись попытки оплаты, подписанный `CONFIRMED` webhook,
  захваченный платёж и созданный заказ. Повтор webhook не создал второго платежа,
  заказа или записи inbox; статус сменился с `pending/pending` на
  `confirmed/ready`. `Init` и `GetState` здесь заменены предсказуемыми ответами
  в памяти — запросов в банк не было. Сид подключает Т-Банк к RU-региону,
  сохраняет другие настроенные методы и удаляет `pp_system_default`.
  Medusa принимала системную сессию даже вне региона и позволяла завершить
  заказ без списания; Store API теперь отвечает 400 на её выбор. Без Т-Банка
  новый RU-регион остаётся без метода оплаты.
  26 сентября DEMO-терминал подключён к рабочему backend на Timeweb. На новой
  RUB-корзине Store API создана платёжная сессия, открыта настоящая форма
  Т-Банка и оплачена тестовой картой. Банковский `GetState` вернул `CONFIRMED`
  с ожидаемой суммой и идентификатором сессии. Банк сам доставил через
  `https://api.mariomikke.shop/hooks/payment/tbank` уведомления `AUTHORIZED`
  и `CONFIRMED`; обе записи inbox обработаны. Платёж захвачен, статус
  `pending/pending` сменился на `confirmed/ready`, создан ровно один заказ.
  Повтор подписанного webhook с каноническими полями уже полученного
  `CONFIRMED` вернул `200 OK`: остались одна запись каждого статуса inbox,
  одна попытка оплаты, один платёж и один заказ, конфликтов нет. Этот повтор
  отправлен вручную после реальной доставки банком, а не повторно банком.
  Партнёр получил письмо Т-Банка об этом DEMO-платеже: `OrderId` и
  ID транзакции совпали с серверной платёжной сессией. Согласно
  [документации тест-кейсов Т-Банка](https://developer.tbank.ru/eacq/intro/errors/test-cases),
  при терминале `DEMO` реальные деньги не списываются. Банковское письмо
  партнёру не подтверждает отправку писем сайтом. Полный путь через интерфейс
  витрины Vercel и доставку писем/Telegram от сайта не проверяли.
  `order.placed` Medusa возникает до авторизации платежа и не
  запускает оповещения; `tbank.order.paid` передаёт уведомление локальному
  email-провайдеру. Без связи с заказом оповещения не отправляются, платёж
  остаётся на сверке/ручном разборе.
- СДЭК: реализованы расчёт тарифов 136/137, поиск городов, выбор ПВЗ и
  курьерская доставка. На рабочем API подтверждены OAuth (в том числе ответ с
  длинным токеном) и тариф для иллюстративной посылки из Москвы, код города 44.
  Реальные отправления не создавались. В шаблонах заданы согласованные цены
  покупателя: СДЭК ПВЗ 350 ₽ и курьер СДЭК 490 ₽; расчёт перевозчика хранится
  отдельно и не подменяет фиксированную плату.
- Яндекс Маркет ПВЗ: выбор пункта и расчёт тарифа по рабочему API проверены для
  условной посылки. Локально реализована фиксированная плата покупателя через
  обязательную положительную `YANDEX_DELIVERY_PVZ_PRICE_RUB`; расчёт перевозчика
  сохраняется отдельно. Публичная `customer_cost` и сумма доставки Medusa используют
  один тариф; без подтверждённого ПВЗ, замеров и доступного расчёта оплату не разрешать.
  Прошли 49 unit-проверок Яндекса, 3 проверки платёжной политики, backend typecheck
  и локальный HTTP smoke поиска города/ПВЗ, фиксированной цены и отказов.
  Согласованная цена покупателю — 350 ₽, внесена в оба backend env-шаблона;
  изменения не развернуты. Сотрудники сами собирают вещи и отвозят посылку
  перевозчику: магазины не являются точками вызова курьера Яндекса.
  19 октября `warehouses/list` вернул HTTP 200 и пустой список складов,
  но `pickup-points/list` с `available_for_dropoff=true` — HTTP 200 и
  1 747 принимающих пунктов в Москве. Для самостоятельной сдачи склад
  регистрировать только из-за пустого списка не требуется: нужна выбранная
  сотрудниками точка, поддерживаемая договором/API. В работающем backend
  `YANDEX_DELIVERY_ENABLED=false`, `YANDEX_DELIVERY_SOURCE_STATION_ID` не задан.
  Самостоятельно точку не назначали; отправление не создавалось.
  См. [инструкцию проверки](../medusa-prototype/INTEGRATION_CHECKS.md#yandex-delivery).
- Telegram и SMTP-провайдеры уведомлений реализованы в backend.
  19 октября runtime smoke настоящего paid-order subscriber передал
  сотрудникам выбранный магазин и покупателю инструкцию о ручном звонке;
  транспорт был локальным. В работающем контейнере read-only подтверждены
  `smtpConfigured=false`, `telegramConfigured=false`, терминал банка DEMO.
  Проверялось только наличие настроек, секреты не выводились. Реальная
  доставка уведомлений пока не подтверждена: без рабочих каналов письмо
  остаётся только в локальном журнале. Готовность/выдача не автоматизируются
  начальным письмом; сотрудники собирают заказ и звонят покупателю.
- Резервные копии: последний серверный архив
  `medusa_20261010_154405.dump.gz` прошёл `gzip -t` и `pg_restore --list`
  (1041 строка). 11 октября архив **успешно восстановлен** с
  `pg_restore --exit-on-error` в отдельный PostgreSQL 15.19: 21 черновик,
  12 опубликованных товаров, 2 уведомления и 1 попытка оплаты Т-Банка.
  Изолированный контейнер без сети, томов и опубликованных портов удалён;
  действующие БД и сервисы не менялись. Это проверка восстановления БД,
  **не** резервирования медиа или восстановления всей витрины. Серверный
  каталог `static` пуст; 36 изображений товаров указывают на файлы
  витрины `/products/`, 21 — на placeholder. Копия файлов витрины и
  хранение архивов вне сервера не подтверждены.
- Локально: Compose передаёт ключи DaData и параметры SMTP/Telegram только
  backend. Собственный курьер выключен, пока не заданы одновременно
  `OWN_COURIER_ENABLED=true`, согласованная `OWN_COURIER_PRICE_RUB` и оба ключа
  DaData. Яндекс, СДЭК и свой курьер при повторном импорте получают
  рассчитанную цену; СДЭК требует обе явно согласованные цены покупателю,
  иначе не включается. Старая бесплатная MVP-опция и выключенные перевозчики
  получают правило недоступности в списке способов доставки. Эти изменения
  **не опубликованы на сервере**.
- В локальном checkout при доступном способе самовывоза теперь показаны
  подтверждённые сборка 1–2 рабочих дня, хранение 7 дней и уведомление по
  телефону. Проверено в браузере с изолированными ответами Store API без
  создания заказа; на рабочем сервере пока доступна только старая MVP-доставка,
  поэтому это не означает включение самовывоза в production.
- Т-Банк в локальном коде не создаёт и не переиспользует ссылку на оплату без
  выбранной доставки. Сумма доставки включается в платёж и отдельную строку
  чека; СДЭК и свой курьер требуют показать и повторно подтвердить покупателю
  итог после серверного расчёта, при смене корзины/суммы повторить подтверждение.
  Локальные unit-тесты и сборка прошли, но HTTP checkout на реальной корзине
  требует PostgreSQL, а визуальная проверка полного шага — доступного backend.

### Зафиксированные доменные решения

- Продажи первого релиза только в России и в рублях.
- УСН "доходы" и НДС 5%; цены вводятся с НДС.
- 100% предоплата.
- Товары маркируются в "Честном Знаке"; продавец работает как производитель.
- Внешний ключ товара для 1С и повторного импорта: артикул/SKU. Нельзя менять
  его после создания товара.
- Вариант без размерной сетки хранится как `ONE SIZE`.

Подробные инварианты данных находятся в `docs/adr/0001-domain-invariants.md`.

## 3. Подтверждённые правила заказчика

### Склады и наличие

- Магазины: Новомосковский, Принц Плаза, Avenue Southwest, Говорово, Небо,
  Райкин Плаза, Водный, Отрада, РИО Дмитровское шоссе и Красный Кит.
- Подтверждённые точки отгрузки: Говорово (108811), Принц Плаза (117574),
  Авеню (119571). После сборки нескольких товаров отправляется одна посылка.
- Если в магазине остаётся одна единица, она не должна быть доступна к покупке
  на сайте.
- Покупатель видит только статус "В наличии", не точное число единиц.
- Если позиции заказа находятся в разных магазинах, команда сначала собирает
  их вместе, затем отправляет покупателю одной доставкой.
- Самовывоз Водный, Говорово и Небо: 1–2 рабочих дня до готовности, хранение
  7 дней, статус готовности и уведомление покупателя по телефону подтверждены.
  Собственный курьер внутри МКАД — ежедневно 12:00–22:00 с звонком перед
  выездом. Почта России не входит в первый запуск; доставка обязательна с
  первого дня.

### Доставка и возвраты

- Внутри МКАД доставляет собственный курьер.
- Для покупателя фиксировано: СДЭК ПВЗ 350 ₽, курьер СДЭК 490 ₽,

- Обратную доставку товара надлежащего качества оплачивает покупатель.
- Возврат денег подтверждается сразу после физического получения товара.

### Архитектурное расхождение

`ADR-001` сейчас предполагает резервирование одного заказа в одной складской
локации без сплит-отгрузок. Новый процесс заказчика допускает сбор позиций из
нескольких магазинов перед единственной отправкой. До реализации остатков нужно
выпустить новый ADR: либо выбрать одну точку-консолидатор, либо реализовать
внутренние перемещения между магазинами. Это не сплит-доставка для покупателя,
но это мульти-локационный заказ внутри учёта.

Сейчас приложение использует одну складскую локацию и один
`YANDEX_DELIVERY_SOURCE_STATION_ID`: реальное место сборки заказа не
определяется автоматически. Сотрудники собирают заказ и сами отвозят
его перевозчику; в API нужно использовать фактическую станцию сдачи.

Обмен с 1С и остатки отдельных магазинов не реализованы; остатки одной
демонстрационной локации нельзя считать актуальным наличием. 11 октября на
сервере 21 черновик реального каталога, у 20 из них 157 вариантов без веса и
размеров упаковки, карточка 1760 без вариантов. Опубликованы 12 демонстрационных
товаров; старые категорийные оценки у них не относятся к реальным артикулам.
Заказчик подтвердил: в переданной таблице уже вес и габариты упакованных
товаров, повторные замеры каждой отдельной вещи не запрашиваются.
Импорт этих атрибутов в реальный каталог и отправка ещё не проверены.
Для нескольких вещей нужны правила общей упаковки и параметры итоговой
посылки; доставка нескольких единиц сейчас блокируется, а не рассчитывается
по одной вещи. При ручном возврате адрес сообщает менеджер после
согласования заявки; единый заранее опубликованный адрес не является
техническим блокером этого процесса.

## 5. План до запуска

Этапы идут в указанном порядке. Внутри одного этапа задачи можно выполнять
параллельно, если они не меняют одну и ту же модель данных.

### Этап A. Тестовая оплата и надёжность backend

**Цель:** покупатель проходит полный тестовый checkout до созданного заказа.

1. **Выполнено 2026-09-26:** секреты только DEMO-терминала добавлены в
   server-only `.env.production`, вне Git.
2. **Выполнено:** переменные переданы в Docker Compose, проверенный backend
   развёрнут без изменения PostgreSQL, Redis и Caddy.
3. **Выполнено:** у RU-региона остался только `pp_tbank_tbank`, бесплатного
   `pp_system_default` нет.
4. **Выполнено:** настоящий `Init`, форма DEMO-банка, подтверждение картой,
   полученный от банка webhook и один оплаченный заказ на сервере; ручной
   подписанный повтор того же уведомления не создал дублей.
5. **Локально реализовано, не развернуто:** минутная
   `tbank-payment-reconciliation` продолжает обрабатывать webhook и после
   15 минут проверяет через `GetState` попытки без подтверждённого webhook.
   Перед проекцией `CONFIRMED` сверяет терминал, PaymentId, сессию и сумму;
   банковское наблюдение фиксируется отдельно от подписанного inbox.
   Ограничение — пять опросов с арендой, задержками и ручным разбором.
   Очередь Admin API показывает зависшие попытки; retry/resolve требуют
   администратора и причины, сохраняют журнал и **не списывают деньги**.
   Офлайн-тесты сверки и миграции на отдельной PostgreSQL прошли; рабочие
   SMTP/Telegram-каналы не настроены, уведомление человеку о проблемной
   оплате не подтверждено. Новые job и миграция на рабочем сервере не
   запускались.

**Критерий DEMO-оплаты через backend выполнен:** тестовая карта создаёт
оплаченный заказ, повтор webhook не создаёт второго заказа или платежа.
Это не проверка боевого терминала, фискального чека или браузерного checkout
витрины.

Локальный тест `apps/backend/integration-tests/http/checkout-tbank.spec.ts`
исполняет Store API, webhook, подписчик и PostgreSQL без сети банка. Для
повторения нужны локальная PostgreSQL, отдельный пользователь с правом создавать
тестовые БД и переменные `DB_HOST=localhost`, `DB_PORT`, `DB_USERNAME`,
`DB_PASSWORD`; в `medusa-prototype/apps/backend` запустить
`npm run test:checkout:offline`. Скрипт подставляет только фиктивные реквизиты
банка, отключает Redis/SMTP и внешние службы доставки; тестовые БД создаёт
Medusa test runner. Оплата DEMO-картой и повтор локального webhook отдельно
проверены на изолированной базе. На рабочем сервере 2026-09-26 подтверждены
отдельно реальная доставка webhook банком, оплаченный заказ и безопасный
ручной повтор. Публичный `/checkout` после деплоя Vercel показывает временную
заглушку: сквозной checkout с витрины не проверен. Не открывать его покупателям
на DEMO-терминале без боевой оплаты и фискализации.

### Этап B. Правовые страницы и коммуникации

**Цель:** витрина готова к модерации банка и честно описывает покупателю процесс
покупки.

1. Сверить оферту, политику и согласие с юристом/заказчиком.
2. Заполнить домен, e-mail, реквизиты и ссылки на службы доставки.
3. **Локально выполнено:** HTML и DOCX описывают фиксированные платные тарифы
   СДЭК/Яндекса и бесплатного собственного курьера внутри МКАД до конца 2026 года.
4. Опубликовать утверждённые оферту, политику, условия доставки и возврата.
5. Разделить согласие на исполнение заказа и отдельные необязательные согласия
   (маркетинговая рассылка, если она появится).
6. Проверить уведомление Роскомнадзора и перечень обработчиков персональных
   данных с ответственным лицом компании.

**Критерий готовности:** все ссылки checkout ведут на финальные документы без
шаблонных полей; документы согласованы с представителем бизнеса/юристом.

### Этап C. Каталог и первичный импорт

**Цель:** админка и витрина содержат реальный, устойчивый к повторному импорту
каталог.

1. Подготовить шаблон импорта: артикул, название, категория, цена, размеры,
   состав, страна, уход, обмеры, вес, габариты и фотографии.
2. Получить и очистить первую таблицу товаров и соответствие файлов фотографий
   товарам.
3. Импортировать каталог через upsert по артикулу/SKU.
4. Проверить карточки, варианты, размеры, доступность и цены на витрине.
5. Настроить безопасное постоянное хранение медиа и резервное копирование.

**Критерий готовности:** повторный импорт не создаёт дубли, карточки содержат
обязательные сведения, изображения отображаются в админке и на витрине.

### Этап D. Склады, остатки и 1С

**Цель:** нельзя продать товар, которого нет в доступном для интернет-заказа
остатке.

1. Принять ADR о сборке из нескольких магазинов и точке-консолидаторе.
2. Создать складские локации магазинов и отметить доступные для онлайн-отгрузки.
3. Реализовать страховой остаток: доступно онлайн только количество больше 1.
4. Спроектировать обмен с 1С: товары, цены, остатки, заказы, оплаты, возвраты
   и статусы.
5. Реализовать начальную загрузку и идемпотентную синхронизацию по артикулу.
6. Добавить мониторинг ошибок и ручной повтор обмена.

**Критерий готовности:** изменение остатка в 1С своевременно меняет доступность
на сайте; последний экземпляр не покупается онлайн.

### Этап E. Маркировка и фискализация

**Цель:** каждая физическая единица корректно проходит продажу, передачу и
возврат.

1. Согласовать с бухгалтером кассовые параметры и выбрать/подключить кассу.
2. Хранить DataMatrix-код на уровне единицы товара, а не товара или варианта.
3. Реализовать сканирование при сборке, валидацию и закрепление кода за заказом.
4. Сформировать чек "Предоплата 100%" после успешной оплаты.
5. Сформировать закрывающий чек "Полный расчёт" при передаче товара покупателю.
6. Обработать ошибки `NotificationFiscalization`, повторную отправку и сверку.
7. Реализовать возвратный чек и возврат маркировки в корректный статус после
   физического получения товара.

**Критерий готовности:** тестовый заказ с маркированным товаром проходит оплату,
сборку, выдачу и возврат с корректным журналом событий и кассовыми чеками.

### Этап F. Доставка

**Цель:** менеджер может отправить заказ, а покупатель получает понятный способ
доставки и отслеживание.

1. Утвердить службы первого релиза, CDEK-режимы и самовывоз.
2. Реализовать CDEK: города, ПВЗ, курьер, тарифы, создание отправления, трек и
статусы.
3. Добавить отдельный способ "Курьер внутри МКАД" с внутренним назначением
курьера.
4. Показывать покупателю бесплатную доставку по утверждённым правилам и хранить
реальную себестоимость отдельно.
5. Добавить обратную доставку в процесс возврата.

**Критерий готовности:** тестовый заказ создаёт корректную отправку, покупатель
видит её статус, а менеджер получает данные для сборки и отгрузки.

### Этап G. Операционная админка и уведомления

**Цель:** четыре сотрудника могут безопасно вести заказ без ручной работы в БД.

1. Создать учётные записи, роли и минимально необходимые права.
2. Настроить Telegram-чат и SMTP-почту.
3. Уведомлять о новом заказе, оплате, ошибке оплаты, ошибке чека, необходимости
сборки, отправке и возврате.
4. Добавить журнал действий: изменение цены, остатка, статуса заказа и возврата.
5. Описать короткие инструкции для менеджера и логиста.

**Критерий готовности:** у каждого сотрудника своя учётная запись; критические
события доходят до ответственного канала, а действия можно проверить.

### Этап H. Личный кабинет и возвраты покупателя

**Цель:** покупатель сам видит заказы и может начать возврат, не раскрывая чужие
данные.

1. Выбрать безопасный способ входа: код по телефону или e-mail.
2. Реализовать сессии, ограничение частоты запросов и срок жизни кода.
3. Добавить историю заказов, адреса и статусы доставки.
4. Добавить заявку на полный/частичный возврат согласно утверждённому правилу.
5. Связать возврат с получением товара, маркировкой, чеком и возвратом оплаты.

**Критерий готовности:** покупатель видит только свои данные и может создать
заявку на возврат; менеджер завершает её без ручных несогласованных операций.

### Этап I. Предзапусковая проверка

**Цель:** подтвердить готовность к приёму первых реальных заказов.

1. Проверить все юридические страницы, контакты и реквизиты.
2. Пройти модерацию Т-Банка и подключить боевой терминал.
3. Выполнить сценарии: успешная оплата, ошибка оплаты, дублирующий webhook,
нет остатка, доставка, маркировка, полный и частичный возврат.
4. Настроить резервные копии PostgreSQL и медиа; проверить восстановление.
5. Проверить логи, доступы, HTTPS, секреты и сроки обновления каталога.
6. Провести обучение сотрудников и ограниченный soft launch.

**Критерий готовности:** согласованный чек-лист пройден, банк активировал
приём платежей, команда умеет обработать тестовый заказ от оплаты до возврата.

## 6. Порядок приоритетов сейчас

1. Этап A: тестовый checkout Т-Банка.
2. Этап B: привести правовые документы к публикуемой редакции.
3. Этап C: получить и импортировать реальный каталог.
4. Принять ADR о мульти-локационной сборке.
5. Этапы D и E: 1С, остатки, маркировка и касса.
6. Этап F: доставка.

Личный кабинет, накопительные скидки, СНГ и дополнительные доставки следует
планировать после устойчивого первого релиза, если они не станут условием
запуска со стороны заказчика.

## 7. Работа с документами и секретами

- Исходные документы в `docs/company docs` не следует коммитить в публичный
  репозиторий: они содержат персональные и банковские реквизиты.
- В Git можно хранить только согласованный текст, который должен быть публично
  доступен на сайте, без внутренних приложений и исходных файлов.
- Ключи Т-Банка, CDEK, SMTP, 1С и Telegram хранятся только в environment-файлах
  сервера или защищённом менеджере секретов, никогда в исходниках и документах.
- Юридические и бухгалтерские решения утверждаются заказчиком, юристом и
  бухгалтером; этот план не заменяет такую проверку.
