# Учение по восстановлению БД — 2026-07-27

- **Задача roadmap:** OPS-003 («Провести restore drill»). Критерий приёмки —
  «Fresh PostgreSQL volume восстановлен; Medusa проходит smoke test».
- **Статус:** критерий выполнен. Восстановление совпало с источником до строки,
  Medusa стартовала на восстановленной базе и ответила `200` на `/health`.
- **Где проводилось:** локальная машина (Windows 11, Docker Desktop, Git Bash).
  На сервере учение **не** повторялось — см. §7.
- **Что проверялось:** цепочка `pg_backup` → свежий том → `scripts/restore-db.sh`
  → запуск Medusa. Первый реальный прогон после починки скриптов (AUDIT.md,
  находки 4.13–4.15): до этого документированный путь восстановления не
  запускался ни разу.

## 1. Сценарий

Учение имитирует потерю тома с данными. Роль «боевой» базы играет
dev-PostgreSQL (`mario_mikke_medusa_postgres`, 127.0.0.1:5433) — единственная
база с реальным каталогом. Роль восстанавливаемой — postgres из
`compose.production.yml` (проект `mario-mikke`, 127.0.0.1:5432).

1. Снять дамп с источника ровно той логикой, которой пользуется сервис
   `pg_backup`.
2. Снести том восстанавливаемой базы и создать заново — стартовое состояние
   должно быть пустым, а не «почти правильным».
3. Восстановить дамп через `scripts/restore-db.sh`.
4. Сверить содержимое с источником.
5. Поднять Medusa на восстановленной базе и проверить, что она работает.

## 2. Команды и результаты

### 2.1. Дамп источника

Выполнен той же последовательностью, что и в `entrypoint` сервиса `pg_backup`:
`pg_dump -Fc` во временный файл → проверка `pg_restore --list` → `gzip` →
публикация → ротация. Запущен в одноразовом `postgres:15-alpine` в сети
dev-компоуза, чтобы не отличаться от боевого сервиса, который тоже ходит по TCP
из отдельного контейнера:

```bash
docker run --rm --network medusa-prototype_default \
  -e PGPASSWORD=... -v "$PWD/backups":/backups postgres:15-alpine sh -c '
    set -eu
    TS=$(date +%Y%m%d_%H%M%S)
    TMP="/backups/.medusa_$TS.dump.part"
    if pg_dump -h postgres -U medusa -Fc medusa_backend > "$TMP" \
      && pg_restore --list "$TMP" > /dev/null 2>&1; then
      gzip -c "$TMP" > "/backups/medusa_$TS.dump.gz"; rm -f "$TMP"
      find /backups -name "*.dump.gz" -mtime +7 -delete
      find /backups -name "*.dump.part" -mtime +1 -delete
      echo "[pg_backup] ok: medusa_$TS.dump.gz"
    else
      rm -f "$TMP"; echo "[pg_backup] FAILED at $TS" >&2; exit 1
    fi'
```

Результат: `backups/medusa_20260726_203153.dump.gz`, 183 002 байта, проверка
оглавления пройдена.

Про происхождение второго файла в каталоге. `backups/medusa_20260726_200433.dump.gz`
остался от первой попытки учения, прерванной инфраструктурным сбоем (см. §5.7).
Что он снят с той же базы и тем же способом, проверено, а не предположено:

| Проверка | `…_200433` | `…_203153` |
|---|---|---|
| Размер в распакованном виде | 537 971 Б | 537 971 Б |
| Записей в оглавлении (`pg_restore --list`) | 1 007 | 1 007 |
| `diff` оглавлений | совпадают полностью | |
| `Archive created at` | `2026-07-26 20:04:33 UTC` | `2026-07-26 20:31:53 UTC` |

Различаются только метка времени внутри архива и, как следствие, размер после
gzip (183 001 против 183 002 байт). Учение выполнено на своём, более свежем
дампе; старый оставлен как есть. Каталог `backups/` закрыт `.gitignore` —
в дампах персональные данные покупателей.

### 2.6. Решение про `medusa db:migrate`

**Миграции при восстановлении не запускаются.** Смысл учения в том, что база из
дампа пригодна как есть; `db:migrate` пересоздал бы недостающие объекты и скрыл
бы неполное восстановление. Medusa стартовала и отдала данные без миграций —
этого достаточно.

Решение проверено отдельным прогоном уже **после** снятия всех сверок, и прогон
выявил серьёзную проблему — см. §3.

## 3. Что нашло учение

### 3.1. `db:migrate` после восстановления портит данные

`medusa db:migrate` выполняет не только миграции схемы, но и *migration scripts*
— обычный код, который пишет в данные. Учёт выполненных скриптов ведётся по
имени файла **вместе с расширением**: в `@medusajs/framework`
`getPendingMigrations` фильтрует по `basename(script)`, и `insertMigration`
пишет туда же `basename`. Скрипт, отработавший через ts-node
(`initial-data-seed.ts`), и он же из сборки (`initial-data-seed.js`) — две
разные записи в `script_migrations`.

Дамп снят с dev-базы, где сид выполнялся через ts-node. В восстановленной базе
лежит запись `initial-data-seed.ts`, сборка ищет `initial-data-seed.js`, не
находит — и запускает сид заново, поверх восстановленных данных. Измеренный
результат на восстановленной базе:

| Таблица | До `db:migrate` | После |
|---|---|---|
| `store_currency` | 3 (`rub`, `eur`, `usd`) | **1** (`rub`) |
| `stock_location` | 1 (`European Warehouse`) | 2 (+ `Основной склад`) |
| `stock_location_address` | 1 | 2 |
| `sales_channel_stock_location` | 1 | 2 |
| `location_fulfillment_provider` | 1 | 2 |
| `tax_rate` | 0 | 1 |
| `script_migrations` | 6 | 7 |

Сид написан идемпотентно в пределах своих допущений, но допущения не совпали с
восстановленной базой: `updateStoresWorkflow` передаёт `supported_currencies`
списком и тем самым **заменяет** его, а проверка существования склада не узнала
`European Warehouse` и создала второй.

Тот же прогон добавил 6 записей в `mikro_orm_migrations` (173 → 179) — это уже
не про сид, а про то, что источником был dev: все шесть принадлежат
`@medusajs/workflow-engine-redis`, который в dev не зарегистрирован. Подробнее
в §5.4.

Что сделано:

- `scripts/restore-db.sh` после успешного восстановления читает
  `script_migrations` и, если там есть записи с `.ts`, печатает предупреждение с
  прямым указанием не запускать `deploy.sh` на этой базе. Проверка не меняет базу
  и не влияет на код возврата — проверено на обоих исходах (записи есть /
  записей нет).
- `DEPLOYMENT.md`: раздел про восстановление говорит, что восстановление
  заканчивается `restart medusa`, а не `deploy.sh`, с объяснением механизма и
  командой для ручной сверки `script_migrations`.

Сам сид не трогался: он лежит в `apps/backend/src/migration-scripts/`, где в этот
момент шла параллельная работа. Правку идемпотентности стоит завести отдельной
задачей — см. §7.

Оговорка про масштаб. На сервере production всегда исполняет `.js`, поэтому
после первого же деплоя запись становится `.js` и повторов не будет. Опасен
конкретный сценарий: восстановление в production дампа, снятого с окружения, где
скрипты гонялись через ts-node, — то есть ровно то, чем занимается это учение и
чем будет первичное наполнение боевой базы данными прототипа.

### 3.2. Compose съедал `$` в хеше пароля админки

Найдено на прерванной первой попытке, проверено заново. `compose` раскрывает
`$VAR` в значениях файла из `--env-file`, а bcrypt-хеш всегда имеет вид
`$2a$14$<соль+хеш>`: часть после третьего `$` — синтаксически корректное имя
переменной, и compose подставляет вместо неё пустую строку.

Проверено на отдельном compose-файле с реальным хешем:

| В `--env-file` | Что получил контейнер |
|---|---|
| `$2a$14$e4tdUXjlEnJRt3A8FnL8COX5qWWpUqV8X6uImLNbw/f65tVcyCy6i` | `$2a$14/f65tVcyCy6i` |
| то же, с удвоенными `$` | значение целиком, без потерь |

Обрубок перестаёт быть валидным bcrypt, и пароль, который `deploy.sh` печатает
как «сохраните прямо сейчас», не подошёл бы никогда, а причина по сообщению
compose не читается.

Тот же дефект наблюдался вживую на учебном `.env.production`: команда проверки
из `DEPLOYMENT.md` вернула `$2a$14` вместо всего placeholder-хеша, и `compose`
на каждый вызов печатал `variable is not set` с куском хеша в качестве имени
переменной. После удвоения `$` значение доходит целиком, а `compose config
--quiet` замолкает.

Что сделано (правки унаследованы от первой попытки, перепроверены и оставлены):

- `scripts/deploy.sh` — `printf '\nADMIN_BASIC_AUTH_HASH=%s\n' "${ADMIN_HASH//\$/\$\$}"`.
- `.env.production.template` и `DEPLOYMENT.md` — требование удваивать `$` при
  ручной установке плюс команда, которая показывает, что реально пришло в
  контейнер. Команда выполнена, работает и дефект ловит.

## 4. Что не подтвердилось

Опасение, что предыдущая попытка оставила «почти правильный» том и сверка
показывает не восстановление, а остатки прежних экспериментов. Проверено:
том пересоздан, пустое стартовое состояние зафиксировано, восстановление
пройдено заново целиком. Совпадение счётчиков получено дважды, на двух
независимых прогонах.

## 5. Ограничения учения

Перечислено то, что делает результат слабее полноценной проверки на сервере.

1. **Не сервер.** Windows 11 + Docker Desktop. Права на файлы, поведение
   `network_mode: host`, ёмкость диска и скорость I/O отличаются от Linux-VPS.
2. **Medusa запущена локальным процессом, а не сервисом компоуза.** Сервис
   `medusa` объявлен с `network_mode: host`, который на Docker Desktop работает
   не так, как на Linux: контейнер не видит `127.0.0.1` хоста напрямую. Запуск
   выполнен из `apps/backend/.medusa/server` — того самого каталога, который
   Dockerfile копирует в `/app`, — так что исполнялся тот же собранный артефакт
   и та же команда `medusa start`. Не проверены: сборка образа, `USER node`,
   `HEALTHCHECK` контейнера и работа Caddy перед бэкендом.
3. **Redis отдельным контейнером на 6380.** Redis из `compose.production.yml`
   слушает 6379, который занят dev-инстансом. Отличие только в порте и в том,
   что учебный Redis не проходил через compose.
4. **Источник данных — dev-база, а не production.** Production-базы ещё нет.
   Следствие: в dev не зарегистрирован `@medusajs/workflow-engine-redis` (он
   подключается только при заданном `REDIS_URL`), поэтому шести его миграций в
   дампе нет. Схема dev-дампа на 6 миграций отстаёт от того, что ожидает
   production с Redis. На боевом сервере это отличие исчезнет, но дамп из dev
   в production переносить нельзя без осознанного `db:migrate` — с оглядкой на
   §3.1.
5. **Дамп снят вручную, а не сервисом `pg_backup` по расписанию.** Выполнена та
   же последовательность команд, но сам сервис с `restart: unless-stopped`,
   суточным циклом и ротацией по `-mtime +7` в работе не наблюдался.
6. **Каталог `backups/` не выгружался никуда за пределы машины.** OPS-002 (S3)
   заблокирован; учение проверяет восстановление из локальной копии, а не
   доступность копии после потери машины.
7. **Первая попытка учения оборвалась** на середине из-за инфраструктурного
   сбоя, не связанного с предметом. Результаты этого протокола получены
   повторным прогоном с нуля; унаследованными остались только правки из §3.2,
   и они перепроверены.

## 6. Остаточные риски

| Риск | Почему остаётся |
|---|---|
| Повторный запуск сида по восстановленным данным | Предупреждение в `restore-db.sh` и запись в `DEPLOYMENT.md` — это ограждение, а не починка. Сам `initial-data-seed` по-прежнему заменяет `supported_currencies` целиком и не узнаёт существующий склад |
| Восстановление на сервере не проверено | См. §5.1–5.2: образ, непривилегированный пользователь, healthcheck контейнера и Caddy не участвовали |
| Бэкап существует только на диске машины | OPS-002 заблокирован отсутствием S3. Потеря диска = потеря всех копий |
| Сервис `pg_backup` в работе не наблюдался | Проверена логика, а не суточный цикл и ротация |
| Время восстановления не измерено как RTO | На 183 КБ дампа оно неинформативно; на боевом объёме требуется отдельный замер |
| Дамп не шифруется | Файл содержит персональные данные покупателей. Сейчас защищён только правами на каталог |

## 7. Рекомендации

1. **Повторить учение на сервере** после OPS-004/OPS-005, полным компоузом,
   включая сборку образа, Caddy и `pg_backup`. Настоящий критерий — восстановление
   средствами, которые есть на сервере, без локальной машины.
2. **Починить идемпотентность `initial-data-seed`** (файл в `apps/backend/src/`,
   отдельная задача): не заменять `supported_currencies` целиком и искать
   существующий склад по устойчивому признаку, а не по имени. Ограждения из §3.1
   после этого останутся как страховка.
3. **Закрыть OPS-002** — без внешней копии восстановление защищает только от
   порчи данных, но не от потери машины.
4. **Замерить RTO** на реальном объёме, когда появятся боевые данные.
5. **Решить, как шифровать и вывозить дампы**: в файле персональные данные.
